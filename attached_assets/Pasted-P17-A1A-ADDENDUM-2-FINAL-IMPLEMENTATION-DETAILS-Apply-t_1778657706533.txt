P17-A1A ADDENDUM 2 — FINAL IMPLEMENTATION DETAILS

Apply these final requirements before executing P17-A1A.

1. Deterministic demo resolver ordering

Use:

ORDER BY created_at ASC, id ASC

Rationale:
- created_at ASC captures the semantic intent: the canonical demo creator is the original demo row.
- id ASC is a deterministic tiebreaker if multiple demo rows share the same timestamp.
- In the current DB, both ordering strategies select the same canonical row:
  00000000-…-0000000a1e00 / “Alex”

Do not use unordered LIMIT 1 anywhere in the unauth demo resolver path.

2. Cleanup script must be dry-run by default

The QA cleanup script must not modify rows unless called with an explicit --apply flag.

Default behavior:
- print total is_demo=true count
- print qa_sweep:* demo row count
- print the candidate rows that would be changed
- print the canonical demo row selected by resolveCreator
- exit 0 without modifying anything

Apply behavior:
- only when --apply is passed
- use the same printed filter
- report rows changed
- rerun-safe / idempotent

3. Prefer is_demo=false, not DELETE

For old qa_sweep:* rows, prefer flipping:

is_demo=false

Do not delete rows in this phase.

Reason:
- reversible
- avoids foreign-key/history risk
- removes them from unauth demo resolver selection
- preserves any idea history, feedback, taste calibration, or QA traces

The cleanup script should also report whether candidate rows appear to have inbound references, if easy to check. That can inform a later true-delete cleanup, but deletion is out of scope now.
